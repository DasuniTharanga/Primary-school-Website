# Implemented security

This document describes the implemented controls and their operational boundaries. It is not a certification or a claim that software can never contain a vulnerability.

## Identity and sessions

- Passwords use Node scrypt with a random 16-byte salt, N=32768, r=8, p=1 and a 64-byte derived key. Comparisons are timing-safe.
- New passwords must contain 12–128 characters, letters and numbers. Public signup and client-selected login roles do not exist.
- Authentication uses 32-byte random session tokens. Only their SHA-256 hashes are stored in the database.
- Cookies are HttpOnly and SameSite=Strict. Production adds Secure and the `__Host-` prefix.
- Sessions have an absolute expiry and an idle expiry enforced by the server. Limits default to 8 hours and 60 minutes. At most five sessions are kept per staff account.
- Logout deletes the current session. Password changes, local recovery, account disabling and role changes revoke affected sessions.
- Login errors are identical for an incorrect password and an unknown account. Unknown accounts still perform a password derivation.
- Login attempts are limited per address and per normalised email. Limits are stored in SQLite so restarting the process does not erase them.

## Authorization and request integrity

| Permission                            | Administrator | Content editor | Public visitor |
| ------------------------------------- | ------------- | -------------- | -------------- |
| Read published content                | Yes           | Yes            | Yes            |
| Manage drafts and public content      | Yes           | Yes            | No             |
| Upload school images/PDFs             | Yes           | Yes            | No             |
| Read private contact/admissions data  | Yes           | No             | No             |
| Edit school settings / staff accounts | Yes           | No             | No             |
| Read staff audit log                  | Yes           | No             | No             |
| Change own password                   | Yes           | Yes            | No             |
| Submit a public enquiry               | Yes           | Yes            | Yes            |

The API enforces these rules independently of frontend navigation. All mutations require an exact Origin match and a custom request header. Authenticated mutations also require a session-bound CSRF token. Cross-site Fetch Metadata requests are rejected. CORS is not enabled.

Access is rechecked after asynchronous request parsing and before account creation or image storage. Updates to content, settings and enquiries use versions to prevent accidental stale writes. Relevant changes are logged without passwords, raw tokens or enquiry message bodies.

## Data and files

- Queries bind request values through prepared SQL statements. Dynamic table/type choices come from fixed allowlists, not arbitrary user input.
- Text lengths, types, required fields, emails, phone formats, dates, roles, grades, statuses and resource URLs are validated on the server.
- Rich HTML is not accepted. React renders stored text without `dangerouslySetInnerHTML`.
- Public form responses contain references rather than personal records. Enquiries remain administrator-only.
- General API requests, public forms, uploads and password changes have request limits. JSON request sizes and server timeouts are bounded.
- Uploads accept PNG/JPEG/WebP images up to 4 MB and PDFs up to 5 MB. Images are decoded with pixel limits, rotated/resized and re-encoded as WebP, removing embedded metadata.
- SVG and executable uploads are rejected. Names are generated by the server, so uploaded filenames cannot choose storage locations.
- Unlinked or draft media is private. PDF responses use attachment and sandbox headers. Publishing makes linked media publicly available; unpublishing prevents further public access to the server copy.
- Data and backups are outside the served `dist` directory. `.env`, source modules and database paths are not static download paths.
- Database and generated-upload files use restrictive filesystem permissions on systems that support them. On Windows, apply suitable account/NTFS access controls to the host folder.

## HTTP headers

The application server sets Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy and Cross-Origin-Resource-Policy. Production also sets HSTS. The built application loads local assets and does not need inline scripts or third-party CDNs.

## Operational boundaries

- Run the public site through HTTPS and keep the configured Origin exact. Do not use the development server for public hosting.
- Keep the server, Node.js, native image dependencies and installed packages updated.
- Protect the host filesystem and backups: database access can reveal private enquiries. Full-disk/volume encryption is a deployment choice; this app does not encrypt every enquiry column itself.
- Website access is password-based; MFA and email-based password reset are not implemented. Staff password recovery is available to someone who already controls the server.
- Image consent is a staff confirmation control. The school must verify permissions before publication. It cannot retract copies already downloaded by visitors.
- Review records/backups for retention and delete data when no longer needed. There is no automatic retention schedule.
- `TRUST_PROXY` is false by default. Set it true only when a controlled proxy overwrites forwarded-address headers and direct access to the Node server is blocked.
- This version targets one persistent Node process with SQLite. Horizontal multi-instance deployment requires a different/shared data design.
